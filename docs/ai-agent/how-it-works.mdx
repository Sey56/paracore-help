# How Paracore-Gen works

This page covers the implementation details behind [AI Assistants and MCP](./index.mdx) — the parts that matter to safety and to understanding why the agent behaves the way it does. You do not need any of this to use the REPL or Gallery scripts; those run your own code and are documented separately.

## One engine, two trust levels

Both your own code (in the REPL or a Gallery script) and the code Paracore-Gen generates are compiled and run by the **same engine** — the same C#, the same API, the same globals. There is no second, agent-only runtime.

The difference is trust, not capability:

- **Your code** is typed by you, in your own Revit. There is no trust boundary around it.
- **Generated code** is written by a model, not by you. It runs on the same channel, but with an extra capability boundary because it was not typed by a human.

## The REPL channel

Every script — yours or generated — runs on the REPL channel. One thing that channel enforces is the **file path**: a script may read and write only inside the workspace folder, and `System.IO` (`File`, `Directory`, `Path`, `FileStream`) is not available on it. Relative names resolve inside that folder; absolute paths are refused.

This guard exists for the agent's sake, but your own playground inherits it too — so a script you write by hand is confined to the same folder. The Gallery is exempt from this channel guard: Gallery scripts *can* use absolute paths and `System.IO`.

## The agent capability boundary

On top of the channel's path guard, generated code is additionally blocked from the machine capabilities it must not reach:

- **Network access** — `System.Net`, HTTP calls, sockets.
- **Process launching** — starting other programs.
- **Reflection and native interop** — inspecting or calling into code at runtime.
- **Loading external DLLs** from disk.

These are refused at runtime, not just discouraged. The restriction is about *where generated code can reach*, not about what it can compute — the model can still read the model, query parameters, and build geometry; it just cannot reach out to your machine or the network.

## The workspace

The agent's generated scripts read and write inside a workspace folder. By default this is:

```
%LOCALAPPDATA%\Paracore\AgentWorkspace
```

If you need it on another drive, set the `PARACORE_AGENT_WORKSPACE` environment variable before starting Paracore.

`Files.Root` points at this folder from code, so `Files.WriteText("out.csv", ...)` lands inside it.

## View images for the agent

The assistant cannot see Revit's screen. `ExportImage` renders a view to an image file so the agent can **look at what it built or changed** and adjust it. A human who wants a picture of a view uses Revit's built-in *Export to Image* command instead.

## The dialog watcher

Revit reports many failed edits as a modal dialog on its UI thread. Agent code runs on that same thread, so a warning parks the very call that has to return a result: the tool call hangs, the assistant cannot see the warning, and the client eventually times out. The assistant cannot dismiss the dialog itself — it is what is blocked.

Paracore-Gen starts a resident **dialog watcher** thread when the server boots. It watches Revit's windows from outside the blocked call and presses the button a person would press, so the call completes and the assistant can carry on. Servers that only read the model do not start it.

| Dialog | What the watcher does |
|---|---|
| Warning with **OK / Continue / Yes** | Presses the keep-edit button. Revit keeps the change; the assistant corrects the geometry afterwards. |
| **Delete element(s)** button | Never pressed. Removing an element is left to you. |
| **Cancel** with no keep option | Presses Cancel — Revit's own answer. A failed edit rolls back normally. |
| A dialog you opened yourself, or the agent-consent prompt | Left alone. |

The watcher acts only while a Paracore tool call is waiting on Revit. Outside a call it watches and logs but clicks nothing, so it will not close a *Type Properties* editor or another window you opened by hand. The consent dialog that approves agent code for the Revit session is never answered by it. If several Paracore servers are running, only one of them answers a given dialog.

It does not suppress the failure and does not touch the transaction: when an edit fails, Revit still rolls it back. The watcher reads the warning text, records which button it pressed, and that record is appended to the tool result so the assistant can see what happened and adjust. Every action is also written to `%APPDATA%\paracore-data\logs\DialogWatcher.txt`.

To turn it off, set `PARACORE_WATCH_DIALOGS=0` before starting your AI client. Revit's dialogs then stay on screen for you to answer.

## Confirmation gates

Tools can carry a `[Confirm("WORD")]` attribute. The engine re-extracts that word from the source itself at runtime and does not trust the value the caller sends. That means a tool marked `[Confirm("APPLY")]` cannot be run by an automated or API call without the exact word supplied — so bulk, destructive operations stay behind a deliberate gate even when the agent invokes them.

## Approval and safety

- **You see the code before it runs.** Nothing executes unseen.
- **Dangerous operations are restricted**, and a runaway script is stopped automatically.
- **Rollback is available** — the engine can run a script in dry-run mode, rolling back model changes while still producing output files (`not_reverted` keeps the files even on rollback).
